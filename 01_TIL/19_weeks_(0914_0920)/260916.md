## 모의면접 질문

### 둘째날 - 웹

1. HTTP
   - 1. HTTP로 통신하는 것과 HTTPS로 통신하는 것은 실제로 어떤 차이가 있나요? 그리고 로그인이나 결제 같은 서비스에서는 왜 HTTPS를 사용해야 할까요?
     - HTTP란?
       - (일반) HyperText Transfer Protocol, 클라이언트와 서버가 리소스(문서, 이미지, HTML, CSS, JS 등)를 요청-응답 방식으로 주고받기 위한 application layer(응용 계층) 프로토콜. 기본 상태는 payload(전송 데이터)가 암호화되지 않은 평문(plaintext)으로 전송된다.
       - (전문) RFC 9110 (HTTP Semantics)은 HTTP를 분산·협업 하이퍼텍스트 정보 시스템을 위한 stateless (상태 비저장) application-level protocol (응용 계층 프로토콜)로 정의함. HTTP의 전체 아키텍처를 기술하고 공통 용어를 정립하며 모든 버전에서 공유되는 프로토콜 요소를 정의한다고 명시함. 여기서 "stateless"는 서버가 이전 요청의 상태를 유지하지 않고 각 요청을 독립적으로 처리한다는 의미이며, 이 특성이 이후 세션 관리(쿠키, 토큰)가 별도로 필요해지는 이유와 연결된다.
     - TLS란? Transport Layer Security, 전송 계층 보안, 두 통신 주체 사이의 데이터를 암호화하고 상대 서버의 신원을 검증하기 위한 프로토콜. HTTP와 TCP 사이에 위치하며, handshake(핸드셰이크) 과정에서 암호화 방식과 세션 키를 먼저 협상한 뒤 데이터를 주고 받는다.
     - TLS가 붙음으로써 HTTP와의 차이점: payload가 그대로 노출. 중간자가 읽거나 변조가 가능. TLS handshake로 세션 키를 교환한 뒤 payload를 암호화하므로 confidentiality(기밀성)와 integrity(무결성)가 추가된다. 여기에 certificate(인증서) 검증까지 포함되어 authentication(인증)도 확보된다.
     - (암호화 동작 원리: "대칭키, 비대칭키", "RSA")
     - 로그인, 결제 서비스에는 왜 HTTPS가 사용되어야 하는 이유: PCI DSS Requirement 4는 공개 네트워크를 통해 전송되는 카드 소지자 데이터는 강력한 암호화 방식으로 암호화해야 하며, TLS 1.2 이상 전송 구간의 최소 요구 버전이고, TLS 1.3이 권장된다고 규정한다. 벤치마크 문서에는 TLS 구현이 카드 소지자 데이터가 송수신될 때마다 활성화되고 있는지 확인해야 하며, 브라우저 기반 구현에서는 URL에 HTTPS가 표시된 경우, 카드 소지자 데이터를 요청해야 한다고 명시함.
   - 2. HTTPS를 사용하면 데이터가 암호화된다고 하는데, 단순히 데이터를 암호화하는 것 외에 어떤 보안 효과가 있나요?
     - authentication 검증 메커니즘: **handshake** 과정에서 서버는 certificate(인증서)를 제시하고, 클라이언트는 이 인증서가 신뢰된 CA(Certificate Authority, 인증 기관)의 서명 체인(chain of trust)으로 연결되는지 검증함.
     - integrity의 보장 메커니즘: TLS 1.3 이후 AEAD(Authenticated Encrption with Associated Data) 방식만 사용함. CBC 모드 같은 구형 암호화는 confidentiality만 보장하고 암호문이 수정되었는지 확인할 내재적 방법이 없었으며, 내장 인증의 부재는 bit flipping 같은 조작 공격을 허용하는 integrity gap이었음. AEAD는 AES-GCM 같은 알고리즘으로 cryptographic tag를 통해 한 비트의 변경이나 손상도 즉시 탐지하며, 데이터가 변조되면 시스템이 복호화를 거부함. 따라서, 암호화 연산에 결합된 authentication tag 검증으로 integrity가 보장됨.
     - confidentiality만으로 부족한 이유: authentication이 없을 경우, 통신 상대가 정상 서버인지 확인할 방법이 없어 공격자가 두 통신 당사자 사이에 은밀히 위치해 데이터를 가로채고 조작해도 양쪽 모두 직접 통신 중이라고 믿게 되는 man-in-the-middle 공격이 성립한다. integrity가 없을 경우, 암호문 자체는 못 읽어도 특정 바이트를 조작해 평문 결과를 바꾸는 공격이 가능하다(bit flipping). 따라서 로그인, 결제처럼 상대 신원과 데이터 무결성이 모두 중요한 서비스에서는 confidentiality 단독으로는 위협 모델을 방어할 수 없음.
