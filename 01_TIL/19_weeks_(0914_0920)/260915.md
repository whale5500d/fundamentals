(블록 스택 기반 방식)
        1. Python 3.11 변경 이전/이후를 왜 다르게 취급하는가? 3.10 이전의 블록 스택 기반 방식은 try 진입/이탈 시 블록 스택의 push, pop 과정이 매번 실행됩니다. 이는 예외의 발생 유무와 관계없이 무조건 발생하는 고정 비용입니다. 반대로 Zero-cost exception 방식은 예외가 실제로 발생했을 때의 비용을 좀 더 증가시키는 대신, 예외가 없으면 비용을 0에 가깝게 줄이는 방식입니다. 런타임 스택 조작 명령어 자체를 제거하고, 컴파일 시점에 "어느 바이트코드 구간에서 예외가 발생하면 어디로 점프해야 하는가"를 정적 테이블(exception table)로 미리 만들어두어, 예외가 실제로 발생했을 때만 테이블을 조회하여 처리 위치를 찾습니다.
     1. 예외를 성능 최적화 관점에서 어떻게 사용해야 하는가?: 결론적으로 예외는 실제로 예외적인 상황에서만 사용해야 하며, 정상 흐름 제어(control flow)의 대체 수단으로 사용하지 않아야 합니다. 예외의 실제 비용 구조를 이해하고 발생 빈도가 높은 hot path에서만 조건문으로 대체하는 판단입니다.
        1. "발생 빈도가 높은 hot path"란 무엇인가요? hot path란 프로그램 전체 실행 시간 중 반복 실행 횟수가 많은 구간을 의미합니다. 수백만 건의 데이터를 순회하는 반복문이 대표적인 예시입니다.
   - 9. (try-except 사용 기준) 예외가 발생할 가능성이 있는 코드라면 무조건 try-except로 감싸는 것이 좋은 방법일까요? 그렇지 않다면 어떤 기준으로 예외 처리를 해야 한다고 생각하시나요?
     1. try-except 사용 기준: 이 구간에서 예외가 자주 발생하면, 반복 횟수만큼 비용이 누적됩니다. 실패가 드문 구간에서는 EAFP를 유지해도 비용이 거의 발생하지 않습니다. 예외가 드물게 발생하는 경우(딕셔너리 키 대부분이 존재하는 경우)는 EAFP가 유리합니다. 반대로 실패가 빈번하게 예상되는 경로에서는 조건 검사(LBYL)가 성능상 유리합니다. 핵심은 "실패 빈도"와 "반복 횟수"를 곱한 총 예외 발생 건수가 실제 병목인지 여부며, 프로파일링(cProfile 등)으로 측정한 뒤 판단해야 합니다.
4. Iterator/Generator
   - 4. 파이썬의 Iterable과 Iterator의 차이를 설명하고, iter()와 next()의 관계를 설명해 주세요.
     1. Iterable과 Iterator의 차이: Iterable은 `__iter__()` 메서드를 구현하며, iterator를 반환할 뿐, 반복할 값을 하나씩 꺼내주진 않습니다. 반면, Iterator는 반복자를 의미하고, `__next__()` 메서드를 구현합니다. 호출할 때마다 다음 값을 반환하고, 더 이상 값이 없으면 StopIteration을 raise합니다. (Iterator는 Iterable의 부분집합이다.)
     1. iter()와 next()의 관계를 설명: iter()와 next()는 각각 객체의 dunder 메서드(`__iter__`, `__next__`)를 대신 호출해주는 wrapper 함수입니다. 객체가 구현한 메서드를 호출하는 진입점(entry point) 역할만 합니다.
5. Iterator protocol의 확장
   - 5. yield를 사용하는 Generator가 일반적인 함수와 어떻게 다르게 동작하는지 설명해 주세요.
     1. 일반 함수(regular function)란 무엇인가?: 일반 함수는 호출(call)될 때 **실행 프레임(frame)이 생성**되고, 함수 본문을 실행한 뒤 return 문(또는 함수 끝)에서 값을 반환하고 **프레임이 즉시 소멸되는 함수**입니다.
     1. generator function이란 무엇인가?: 함수 본문에 **yield 표현식을 하나 이상 포함**한 함수입니다. 호출하면 함수 본문이 즉시 실행되지 않고, 대신 generator object를 반환합니다. 이 generator object에 대해 next()를 호출할 때마다 yield 지점까지 실행되고, 그 지점에서 실행이 일시 중단(suspend)됩니다. 이때 실행 프레임(frame)은 소멸되지 않고 상태(지역 변수, 실행 위치)를 그대로 보존합니다. 다음 next() 호출 시 중단된 지점부터 실행이 재개(resume)됩니다. (실행 프레임이 보존되어야 하는 예시 찾아보기)
     1. PEP 255 (설계 근거, 이 프레임 보존 구조가 왜 필요한지): PEP 255 원문에 따르면, "값을 여러 번 생성하는 동안 상태(state)를 유지해야 하는 producer 함수"의 문제를 해결하기 위함입니다. producer 함수가 값을 생성하는 사이에 상태를 유지해야 하는 어려운 작업을 수행해야 할 때, 대부분의 프로그래밍 언어는 생성될 때마다 호출되는 콜백 함수를 producer의 인자 목록에 추가하는 것 외에는 만족스럽고 효율적인 해결책을 제공하지 않았습니다. 콜백 기반 방식은 "상태를 어디에 저장할 것인가"는 책임을 호출자 쪽 전역 변수나 별도 상태 머신으로 떠넘기는 구조였지만, generator는 이 상태(지역 변수, 실행 위치)를 함수 자신의 프레임 안에 그대로 보존함으로써, 상태 관리 책임을 함수 내부로 되돌려준 설계입니다. 이것이 "프레임을 소멸시키지 않고 보존"하는 이유입니다.

7. PEP 484 (동적 타입 시스템 + gradual typing)
   - 6. 대규모 파이썬 프로젝트에서 타입 힌트, 예외 처리, Iterator/Generator를 함께 활용하여 안정성과 성능을 확보하려면 어떤 원칙을 적용하시겠습니까? 각각의 장점과 한계도 함께 설명해 주세요.
     1. 대규모 프로젝트란 무엇인가?: 정량적인 정의는 없으나, 실무에서는 코드베이스 규모(수만~수십만 라인 이상)와 협업 인원(다수 개발자가 동일 코드베이스를 동시에 수정)일 때 대규모 프로젝트라고 합니다. 코드 작성자와 코드 사용자(다른 함수에서 호출하는 개발자)가 분리되는 순간부터 "이 함수가 어떤 타입을 받고 어떤 타입을 반환하는가"를 코드만 보고 파악하기 어려워지는 문제가 발생합니다. 소규모 개인 프로젝트에서는 작성자 본인이 문맥으로 기억하므로 이 문제가 두드러지지 않습니다.
     1. 타입 힌트란 무엇인가?: 함수 인자, 반환값, 변수 등에 타입을 명시하는 주석(annotation), PEP 484에서 문법이 도입되었습니다. PEP 484의 설계 목표는 정적 분석(static analysis)을 쉽게 만드는 것입니다. 구체적으로는 mypy 같은 오프라인 타입 검사기(offline type checker) 지원과, IDE의 코드 완성 및 리팩토링 기능을 위한 표준 표기법 제공이 핵심 목표입니다. 이 중 정적 분석 지원이 가장 중요한 목표로 명시됩니다.
     1. 타입 힌트가 대규모 프로젝트에서 필요한 이유: 타입 검사는 별도 도구(mypy, pyright 등)가 코드를 실행하지 않고 정적으로 분석해서 수행합니다. 대규모 프로젝트에서 헙업 인원이 늘어날수록 "이 함수의 입력/출력 타입"이라는 암묵적 계약(implict contract)을 코드 실행 없이 문서화, 검증할 수 있어야 하기 때문입니다. 즉 런타임 이전 단계에서 타입 불일치 버그를 포착하기 위함입니다.
     1. EAFP, Iterator/Generator 원칙과 타입 힌트 간의 결합: 세 원칙은 서로 다른 계층에서 작동하므로 상충하지 않고 병행 적용됩니다.
        1. 함수 시그니처에는 Iterator/Generator 여부를 타입 힌트로 명시할 수 있습니다. (`Iterator[int]`, `Generator[int, None, None]` 등) 이는 호출자가 반환값이 즉시 전체 데이터가 아니라 지연 평가되는 값이라는 것을 코드 실행 없이 알 수 있습니다.
        2. 예외를 발생시킬 수 있는 함수는 docstring이나 타입 힌트 주석으로 어떤 예외가 발생 가능한지 명시합니다.(파이썬은 checked exception을 언어 차원에서 강제하지 않으므로, 관례적 문서화에 해당합니다.)
        3. 타입 힌트가 "무엇이 들어오고 나가는가"를 정적으로 보장하는 동안, EAFP는 "그 계약이 실제로 깨졌을 때 어떻게 복구할 것인가"를 런타임에서 담당합니다. 즉 타입 힌트가 EAFP를 대체하지 않고, 둘은 각각 정적/동적 계층에서 안정성을 나눠 담당합니다.
        4. (세 원칙의 장점과 한계) 세 원칙 모두 "안정성 확보 계층"과 "실행 효율 확보 계층"이 다르다는 공통 한계를 가집니다. 타입 힌트는 정적 계층에서만 동작하고, EAFP와 Generator는 런타인 계층에서만 동작하므로, 어느 하나만으로는 전체 안정성, 성능을 보장할 수 없고 반드시 CI 단계의 정적 검사(mypy 등)와 런타임 테스트를 함께 구성해야 합니다.
