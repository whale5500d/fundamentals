## 4교시

- 논리적으로 헛점을 발견했을 때,
- 화이트보드 사용 방법
- 논리적 허점을 발견하는 것을 즐긴다.

- Memoization: 메모리에 두어서, 계산을 효율적으로 하는 것
  - 추론 과정에서 중복 계산(같은 과정의 연산을 두 번 이상 실시)한다.
  - TC(Time Complexity) vs SC(Space Complexity) (제로섬 게임)
    - 메모리를 덜 쓰고 최적화가 가능하다면, 삼성 / 하이닉스 상폐

---

- KV Cache: LLM 추론 중 이전 토큰의 Key, Value 벡터를 GPU 메모리에 저장해두고, 다음 토큰을 생성할 때 재사용해 중복 Attention 연산을 줄이는 캐시 구조
  - $t\_(n+2) = g(t\_1, ..., t\_n+1)$
  - 추론: 프리필에서 채우고, 디코드에서 재활용한다.
  - 서빙:
  - 순수 추론에 모두 사용하면 안 된다.

---

- Continuous Batcing: LLM 서빙에서 매 Decode 스텝마다 완료된 요청을 배치에서 제거하고, 대기 중인 새 요청을 즉시 추가해 배치 구성을 계속 갱신하는 스케줄링 기법
  - $p_n = (p_1, p_2, ...)$
  - $d_n = (p_1, p_2, ..., p_n, p_(n+1))$
    - $p_3$가 $p_2$보다 먼저 계산되었다면, $p_3$를 제거하고, $p_(n+1)$를 추가
  - MPA를 끝까지 고정

---

- Attention
  - Self Attention
  - Cross Attention
  - Paged Attention: KV Cache를 고정 크기 블록으로 나누어 "비연속" GPU 메모리에 저장하고, Attention 계산 시 필요한 블록을 찾아 참조하도록 만든 KV Cache 관리 방식 (메모리 관리자가 파편화된 메모리가 비연속적이어도 가져올 수 있기 때문, CPU OS에서도 사용됨)
    - Page: 메모리를 고정 크기 블록으로 나눈 단위 (운영체제의 페이지 개념)
    - 기존에는 하나로 이어진 큰 메모리 공간에 할당하는 방식으로 관리했는데, 실제로 얼마나 긴 응답이 생성될지 미리 알기 어렵기 때문에, 메모리를 넉넉하게 잡아 두는 경우가 많다.
    - 리눅스 한 페이지의 크기: 4KB(4096바이트)
    - 칩이라 부르는 가상 메모리
  - Flash Attention

  - (Apache) 최적화하여 오픈 소스 기여

---

- (KV Caching VS)
- Prefix Caching
  - Prefix: 여러 요청이 공통으로 보내는 프롬프트의 앞부분
  - 예시 - 시스템 프롬프트, 모든 프롬프트에 공통으로 사용되는 부분이기 때문, 결국 더 많은 메모리를 차지하게 되는 트레이드 오프

- 여기까지 추론 최적화의 핵심 4가지 기능을 배움

---

- 내 vLLM의 성능 지표를 파악하는 방법을 배우자.

- Throughput(처리량): LLM 서빙 시스템이 단위 시간 동안 여러 요청을 처리하며 생성한 출력 토큰의 총량
  - 100 requests/s: 서버가 1초 동안 100개를 처리
  - LLM 서빙에서는 요청 수뿐 아니라 토큰 수로도 Throughput을 봄.
  - `requests/s`, `output tokens/s`, `total tokens/s`처럼 여러 단위로 표현됨.
  - 1초에 몇 토큰이 출력되는지
  - 개별 요청 하나가 아니라 시스템 전체가 단위 시간에 만들어 낸 결과의 총량
  - 이 시스템에 대한 모든 요청
  - Throughput을 계산하기 위해 날리는 전용 Request가 있음.
  - 실 서비스에서 사용하는 Throughput도 있음. -> 팀 프로젝트 때 있어야 함. 품질 평가가 필요.
  - 인공적인 데이터셋이 현실과 동 떨어질 수 있음. 실 사용자의 프롬프트를 사용하는 것이 중요함.
  - 해피 케이스만 넣게 될 경우가 많음. 테스트 전문가 필요.
  - Cache가 많아야 동시 처리가 가능해짐.

- Latency(지연 시간): 요청을 보낸 시점부터 첫 토큰이 도착하거나 전체 응답이 완료되기까지 걸리는 시간
  - 유저가 이탈할 수 있는 시간이므로, 짧을수록 좋음
  - runpod 사이트: GPU 가격 비교 분석 가능.
  - 국가는 "모두의 AI"에 GPU, 전기, 네트워크, 운영에 사용하겠다는 목표.
  - TTFT(Time To First Token): 요청 후 첫 토큰이 도착하기까지 걸리는 시간
  - TPOT(Time Per Output Token): 첫 토큰 이후 다음 토큰이 평균적으로 생성되는 간격
  - Total Latency: 요청 후 전체 응답이 완료되는 시간

## 5교시

- 지연시간 측정하고 싶은데, 한 번의 측정으로 해결되지 않음. 입력 길이, 동시 요청 수, GPU 상태, 배치 구성에 따라 Latency가 달라질 수 있음
- (SLA) P50, P95, P99 ?? (다른 개발 분야에서도 사용됨)
  - P50: TTFT가 1초라면, 요청 100개 중 50개는 1초 안에 첫 토큰을 받았다는 의미.
  - P95: TTFT가 1초라면, 요청 100개 중 95개는 1초 안에 첫 토큰을 받았다는 의미.
  - P99: TTFT가 1초라면, 요청 100개 중 99개는 1초 안에 첫 토큰을 받았다는 의미.
  - SLA는 정해진 기준: 유료 유저 대상으로 진행하는 경우가 많음.

- FastAPI + LangGraph는 동일
- LLM 모델을 사용하는 방법
  - API LLM(프론티어 모델)
  - 공개 가중치 모델(OpenAI 호환 API 방식 사용)
    - HG T -> GPU가 있는 서버를 띄워야 의미가 있음.
    - vLLM -> GPU가 있는 서버를 띄워야 의미가 있음.

- Tenso Parallelism(TP)
  - 모델 하나를 올리기 위해 GPU를 여러 개 사용해야 함.
  - LLM에 들어가는 연산이라는 게 잘 나눠지고, 잘 합쳐져야 함.
  - vLLM을 만드는 사람이 어려울 내용임.
  - 병렬로 계산했다가 합치고
  - All-reduce
  - Column / Row Parallel

- Speculative Decoding: 작고 빠른 Draft 모델이 다음 토큰 여러 개를 미리 추측하고, 크고 정확한 Target 모델이 그 토큰을 한 번에 검증해서 Decode 속도를 높이는 추론 가속 기법
  - Draft 모델: 다음에 올 가능성이 높은 토큰을 여러 개를 미리 생성
  - Target 모델: 검증 역할. GAN 모델(Discriminator, Generator, 적대적 생성 신경망), 병렬로 진행. 직렬로 하면 순서가 생기기 때문.
  - 일찍 거절되는 문제를 해소하기 위해 Draft 모델이 최소한의 성능이 나와야 함.

- Docker Containerization
