## 기타 데이터베이스 (답안지)

1. DB 모델 비교
   - 2. ✅ 키-값, 문서형, 그래프 데이터베이스의 특징과 각각에 적합한 사용 사례를 설명해 주세요.
        - 키-값: key로 value를 저장하고 조회하는 유형, key 기반의 단일 조회(get)와 저장(put)
          - 세션 저장: 요청마다 session ID 조회해야 함. key 단위로 만료 시간을 지정해서 세션 만료 처리한다.
          - 캐시: 식별자로 계산된 결과 조회해야 함. get 연산으로 빠른 응답에 유리하므로 키-값 DB 사용
          - 카운터: 특정 key의 숫자 반복 증가. key 하나가 카운터 하나에 대응함. Redis의 INCR 같은 원자적 연산을 지원하는 제품이 많아 동시 증가에 값이 어긋나지 않음.
        - 문서형: 계층 구조의 문서(JSON 등)를 저장 단위로 하는 유형, 문서 내부 필드를 조건으로 질의하고 인덱싱(indexing), 문서마다 필드 구성이 달라도 되므로 schema(스키마 — 데이터 구조 정의) 변경이 유연 (ex. 우리 서비스에서 장소DB 구축 시, 장소의 세부 types를 JSON으로 관리했습니다.)
          - 사용자 프로필: 사용자 1명의 정보를 한 번에 조회하고, 필드 조건으로 사용자 검색,
          - 상품 카탈로그
          - 콘텐츠 관리
        - 그래프: 노드 (node)와 관계 (edge)를 저장 단위로 하는 유형, 데이터를 node(개체), edge(개체 간 관계), property(속성)로 표현, 관계를 따라가는 traversal(순회), 관계가 저장 단위이므로 다단계 관계 조회가 핵심 기능
          - 소셜 네트워크: 사용자는 node, 친구 관계는 edge로 저장, 그래프형은 node에서 인접 edge를 따라가는 방식이므로 단계 수가 늘어도 질의가 단순하게 유지
          - 추천
          - 사기 탐지(fraud detection)
        - 관계형 DB와 그래프 DB의 동작 원리
2. Redis (with Cache)
   - 4. ✅ Redis를 캐시로 사용할 때 원본 데이터와 캐시 사이에 불일치가 생기는 이유와 해결 방법을 설명해 주세요.
        - Cache: 원본 조회보다 빠른 응답을 위해 결과의 사본을 저장하는 계층
        - Redis: 메모리 기반 키-값 저장소
        - 원본 데이터(source of truth)
        - 데이터 불일치: 원본과 캐시의 값이 서로 다른 상태
        - 원인
          - 캐시 전략: 읽기/쓰기 시 캐시와 원본을 어떤 순서로 갱신할지 정한 방식. 캐시 전략이 잘못되면 데이터 불일치 문제 발생
          - 이중 쓰기: 원본과 캐시, 두 저장소에 각각 쓰기를 수행하는 구조
          - 경쟁 상태: 동시 요청의 실행 순서에 따라 결과가 달라지는 상황
        - 해결
          - TTL: 키가 자동 삭제되는 만료 시간
          - 캐시 무효화: 원본이 변경될 때 캐시의 해당 값을 삭제하거나 갱신하는 동작
          - cache-aside, write-through, write-behind: 읽기/쓰기 경로에서 캐시와 원본을 연동하는 대표 패턴
