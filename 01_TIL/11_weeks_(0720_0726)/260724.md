# 금 - 특강

## (요약본) 카카오 특강 - 수석 엔지니어는 AI를 어떻게 활용하는가

### 1. 발표 개요

**특강명**: 카카오 특강 — 수석 엔지니어는 AI를 어떻게 활용하는가

**강사 소개**: 카카오 FDE(Forward Deployed Engineer)팀 소속 수석 엔지니어. 해당 팀은 팔란티어(Palantir)의 FDE팀 운영 방식을 모방해 구성됨. 하네스 결과물 제작, 콘텐츠 제작, 논문 제작 등 여러 영역의 작업을 혼자 소화하고 있음.

**핵심 주제**: AI 에이전트(하네스, 서브에이전트, Agent Team)를 활용한 개발·콘텐츠 제작 워크플로우 설계와, 이를 뒷받침하는 도구·정보 습득 프로세스.

---

### 2. 핵심 개념

#### 하네스(harness) / 하네스 엔지니어링

- **문제 상황**: Claude Code에서 도메인별 작업을 처리할 때 매번 에이전트 구성을 수작업으로 설계해야 하는 비효율.
- **부족한 개념**: 하네스, 하네스 엔지니어링의 정의.
- **알게 된 사실**:
  - **하네스**: 특정 도메인 작업을 처리하기 위해 사전 구성된 에이전트 팀(agents) + 스킬(skills) + 오케스트레이션 규칙의 묶음. `.claude/agents/`, `.claude/skills/` 디렉터리 형태로 프로젝트에 배치됨.
  - **하네스 엔지니어링**: 이러한 하네스를 설계·생성·검증하는 작업 자체를 지칭. `revfactory/harness`가 이 작업을 자동화하는 메타 스킬(meta-skill — 스킬을 생성하는 스킬)임.
- **섹션**: AI

#### Dynamic Workflow

- **문제 상황**: 고정된 단일 파이프라인 방식으로는 상황별 작업 흐름 변화에 대응하기 어려움.
- **부족한 개념**: Dynamic Workflow의 정의.
- **알게 된 사실**: 고정된 단일 파이프라인이 아니라, 상황에 따라 에이전트 간 작업 흐름(순차/병렬/위임)이 반복적으로 재구성되는 오케스트레이션 방식. `/effort` 같은 명령이나 자연어 지시("워크플로우 만들어서 작성해줘")로 즉석에서 설계 가능.
- **섹션**: AI

#### Agent Team

- **문제 상황**: 단일 세션 내 서브에이전트(subagent)와 여러 세션에 걸친 협업 방식의 차이가 불명확함.
- **부족한 개념**: Agent Team과 서브에이전트의 구분.
- **알게 된 사실**: Agent Team은 Claude Code의 실험적 기능으로, 서로 독립된 세션의 Claude Code 인스턴스 여러 개가 공유 태스크 리스트와 메시지함(mailbox)을 통해 협업하는 구조. 단일 세션 내에서 컨텍스트를 공유하는 서브에이전트와는 별개 개념. 환경변수 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`로 활성화.
- **섹션**: AI

#### 컨텍스트 로트(context rot)

- **문제 상황**: 긴 대화나 대형 컨텍스트를 다룰 때 모델 응답 품질이 저하되는 현상의 원인 파악 필요.
- **부족한 개념**: context rot의 정의와, 하네스 구조가 이를 완화하는 원리.
- **알게 된 사실**: 입력 프롬프트가 길어질수록 모델의 정확도와 추론 능력이 떨어지는 현상. 하네스/서브에이전트 구조가 이를 완화하는 이유는, 무거운 컨텍스트를 메인 세션이 아닌 격리된 서브에이전트 컨텍스트로 분산시키기 때문임.
- **섹션**: AI

## 3. 실전 사례

#### "에이전트의 시대" 소설(brunch) — 하네스 엔지니어링 구현 과정

- **문제 상황**: 소설 창작 과정에서 과학적 설정의 개연성 검증, 아웃라인 일관성 유지 등 여러 전문 영역의 검토가 필요함.
- **고려한 옵션**: 단일 에이전트로 전 과정 처리 vs 도메인별 전문 서브에이전트 팀 구성.
- **결정 및 이유**: AgentEra 폴더에 `.claude/agents` 구조로 하네스를 구성. 이 구조로 시도하면 적절한 서브에이전트(SubAgent)가 자동 생성됨을 확인 — 예: 과학 자문 에이전트(소설의 과학적 기반을 검증·강화하는 자문 역할).

**진행 순서**:

1. 아웃라인 사전 설계
2. AgentEra `.claude/agents` 구조로 하네스 구성 — 도메인 설명만 주면 적절한 서브에이전트 자동 생성
3. 생성된 서브에이전트(과학 자문 에이전트 등)를 활용해 집필·검증 반복

**Claude Code 공식 문서 대조 결과**: 서브에이전트는 YAML frontmatter를 가진 마크다운 파일이며, 필수 필드는 `name`, `description` 두 가지. 저장 위치는 프로젝트 범위의 `.claude/agents/`(버전 관리 포함, 팀 공유용)와 사용자 범위의 `~/.claude/agents/`(전 프로젝트 공용). `description` 필드를 기반으로 메인 세션이 작업 성격을 판단해 자동 위임(delegation) 여부를 결정함. 이는 `revfactory/harness`가 "도메인 문장 → 아키텍처 패턴 선택 → `.claude/agents/` 자동 생성"이라 설명한 워크플로우와 정확히 대응됨.

## 6. Q&A 정리

### Q1. AI 관련 정보를 어디서 얻는가?

- X.com에서 유명인(Andrew Ng 등) 팔로우
- 링크드인 정보 추천
- AI 뉴스 매체(AI Times)

### Q2. 토큰을 어떻게 관리하는가?

- **Viber Tools** 사용, 토큰을 세밀하게 관리하지 않고 최대치까지 소모하는 방식
- Viber Tools의 정체는 4번(도구·참고 자료) 표 1 항목 5 참고 — 원본 대조 필요

#### Q2-1. 토큰을 최대로 사용해서 확인할 수 있는 인사이트는 무엇인가?

- 새로운 모델의 한계가 어디까지인지 파악하는 것 자체가 인사이트가 됨
- 참고 사이트: Artificial Analysis(https://artificialanalysis.ai)

#### Q2-2. 실제로 인사이트를 얻어본 사례는?

- 같은 계열 모델의 신규 버전과 구버전을 비교(Sonnet 4.8 vs Sonnet 5)하여, 구버전이 처리하지 못하던 작업을 신버전이 얼마나 더 잘 알려주는지 확인
- 발표자가 파악한 바로는 프롬프팅 관련 데이터가 더 많이 학습된 것으로 보임(추정)
- 단, 신규 모델이 구체적으로 무엇을 "더 알려주는지"는 발표자 본인도 명시적으로 확인하지 못한 상태 — 미확정 관찰로 기록

## 7. 본인 인사이트 / 액션 아이템

> 발표 내용이 아닌 본인의 판단·계획

- **문제 상황**: 하네스 기반 에이전트 팀 설계 방식(도메인 설명 → 아키텍처 패턴 선택 → 에이전트/스킬 자동 생성)을 특강에서 관찰함. 본인의 개발 프로젝트나 포트폴리오 구성에도 이 방식을 적용할 수 있을지 검토 필요.
- **고려한 옵션**:
  - 단일 에이전트 방식 유지 (기존 워크플로우 그대로)
  - 하네스 방식 도입 — 프로젝트 도메인별로 전문 에이전트 팀을 구성해 작업 분산
- **결정 및 이유**: 하네스 방식을 개발 프로젝트/포트폴리오 구성에 적용해보기로 함. 특강에서 확인한 6가지 아키텍처 패턴이 실제 소프트웨어 개발 워크플로우(코드 리뷰, 문서화, 데이터 파이프라인 설계 등)에 그대로 대응되는 사례가 harness/harness-100 저장소에서 확인되었기 때문.
