# 스터디

## 다각도 접근 방법

1. **교환 논증(exchange argument)으로 직접 증명하기**: 정렬 기준이나 선택 기준이 왜 최적인지, "그리디 선택을 다른 선택으로 바꾸면 결과가 나빠지거나 동일하다"는 논리를 스스로 세워본다. 이 과정을 거치지 않고 정답만 맞히면, 다음 문제에서 조건이 달라지면 같은 실수를 반복한다.
2. **반례를 직접 만들어보기**: 풀이가 통과한 뒤, "이 그리디 전략이 실패하는 입력이 있을까"를 스스로 설계해본다. 반례를 못 찾으면 최적 부분 구조아 성립한다는 심증이 강해지고, 반례를 찾으면 그 문제는 그리디가 아니라 DP로 접근해야 했다는 신호다.
3. **정렬 기준을 바꿔가며 실험하기**: 그리디는 정렬과 결합되는 경우가 많다. 오름차순/내림차순, 단일 키/복합 키(다중 기준 정렬) 등 정렬 기준을 의도적으로 바꿔서 결과가 어떻게 달라지는 관찰하면, 왜 특정 기준이 정답으로 이어지는지 감각이 생긴다.
4. **그리디로 안 풀리는 문제와 짝지어 보기**: 같은 유형처럼 보이지만 그리디가 실패하고 DP가 필요한 문제(예: 활동 선택 문제 vs 배낭 문제)를 나란히 풀어보면, 최적 부분 구조가 성립하는 경계가 어디인지 체감된다.
5. **문제를 구조별로 분류하기**: 구간 스케줄링(interval scheduling), 동전 교환, 활동 선택, 최소 신장 트리(MST) 계열 등으로 문제를 유형화하면서 각 유형의 공통 증명 패턴을 정리한다. 같은 구조가 반복되는지 스스로 확인하는 과정이다.

"제약 조건 분석 로그"에 이 다섯 가지 중 어떤 방식을 적용했는지 한 줄씩 남기면, 그리디 문제를 풀 때마다 어떤 검증 절차를 거쳤는지 누적 기록으로 남길 수 있다.

## 제약 조건 분석 로그

1. 입력 크기 확인: 문제의 제약 조건(N <= 10^5 등)을 먼저 읽는다.
2. 요구 시간복잡도 역산: 그 입력 크기에서 시간 제한 내 통과 가능한 시간복잡도가 무엇인지 계산한다.(예: N <= 10^5이면 O(NlogN)이하가 안전하다.)
3. 후보 알고리즘 나열: 역산한 시간복잡도를 만족하는 알고리즘 후보를 떠올린다.
4. 선택 이유 기록: 여러 후보 중 왜 그 알고리즘(또는 자료구조)을 선택했는지 근거를 한 줄로 남긴다.

제약 조건만 보고 접근하는 방법을 스스로 유추하는 사고 절차 자체를 체화하는 것이다. 다섯 가지 그리디 검증 방법 중 어떤 것을 적용했는지 로그의 "선택 이유" 항목에 함께 남기면, 그리디 문제 하나를 풀 때마다 어떤 검증 절차를 거쳤는지 누적된다.

## 화이트보드 풀이 방식

설계한 "제약 조건 분석 로그"의 절차를 말로 그대로 재현하는 것이 기본 골격이다. 명확한 순서는 아래와 같다.

1. 문제 재진술(restate)
   - 문제를 읽자마자 코드나 알고리즘으로 바로 넘어가지 않고, 본인이 이해한 문제를 자기 언어로 한 번 요약해서 말한다. "입력은 무엇이고, 출력은 무엇이고, 제약은 무엇인지"를 상대방(면접관 또는 팀원)과 먼저 맞춘다. 이 단계를 생략하면, 문제를 잘못 이해한 채로 20분을 낭비하는 상황이 생긴다.

2. 제약 조건 분석을 소리 내어 말하기
   - "N이 10^5이므로, O(N^2)은 시간 초과 가능성이 높고, O(NlogN) 이하를 목표로 접근해야겠다"처럼, 제약 조건에서 요구 시간복잡도를 역산하는 과정을 그대로 발화한다. 이 부분이 화이트보드 풀이에서 가장 변별력 있는 구간이다. 코드를 짜기 전에 이미 문제 범위를 좁혀냈다는 것을 보여준다.

3. 후보 접근법을 복수로 제시
   - 한 가지 알고리즘으로 바로 확정하지 말고, "그리디로 접근할 수도 있고, DP로도 접근할 수 있는데, 이 문제는 최적 부분 구조가 성립하는지부터 확인하겠다"처럼 후보를 나열한 뒤 근거로 좁혀가는 과정을 보여준다. 정답만 말하면 사고 과정이 드러나지 않는다.

4. 선택한 접근법의 근거 제시
   - 정리한 검증 방법(교환 논증, 반례 탐색 등)을 짧게 언급하며 선택 이유를 말한다. "이 정렬 기준으로 그리디 선택을 했을 때 교환해도 결과가 나빠지지 않는다는 점에서 이 접근이 타당하다"는 식이다.

5. 의사코드(pesudocode) 수준으로 구조 먼저 그리기
   - 바로 문법을 맞춰가며 코드를 짜지 말고, 화이트보드에 함수 흐름이나 핵심 로직만 먼저 그린다. 세부 문법 오류로 흐름이 끊기는 것을 방지한다.

6. 엣지 케이스를 스스로 먼저 제기
   - 상대방이 지적하기 전에 "입력이 빈 배열이거나 N이 1인 경우는 이렇게 처리하겠다"처럼 스스로 엣지 케이스를 짚는다. 이 습관이 있으면 면접관의 질문에 끌려가지 않고 주도권을 유지한다.

7. 구현 후 시간복잡도 재확인으로 마무리
   - 코드를 완성한 뒤, 처음에 말했던 목표 시간복잡도와 실제 구현이 일치하는지 다시 한 번 확인하며 마무리한다. 1단계에서 세운 목표와 마지막 결과를 연결지으면, 설명 전체가 하나의 논리로 이어진다.
