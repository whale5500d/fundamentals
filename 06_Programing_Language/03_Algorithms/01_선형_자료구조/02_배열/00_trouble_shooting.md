# Trouble Shooting

## 260901

### 개념 학습 정리 - 리스트 복사와 참조 할당

**문제 상황**: 정렬 유지 삽입 함수 (`solution`) 구현 중 `result = array`로 복사본을 만들었으나, 삽입 결과가 정렬 위치가 아닌 배열 끝에 추가되는 오류 발생.

**부족한 개념**: 파이썬에서 리스트 할당(`=`)이 값 복사가 아닌 참조 (reference) 할당이라는 점.

**알게 된 사실**: `result = array`는 새 객체를 만들지 않고 동일한 메모리를 가리키는 참조를 생성한다. 따라서 `len(array) == len(result)` 비교가 항상 참이 되어 조건문이 무력화됨. `array.copy()` 또는 슬라이싱 (`array[:]`)을 사용해야 독립된 객체(얕은 복사, shallow copy)가 생성되어 두 리스트가 분리된다.

**개념이 포함된 섹션**: PL

## 260910

### 개념 학습 정리 - 투 포인터 초기 인덱스 경계값

**문제 상황**: 투 포인터(two pointer) 기법으로 두 요소의 합이 목표값과 일치하는 인덱스 쌍을 찾는 문제에서, 오른쪽 포인터를 `right = len(input_list)`로 초기화함.

**부족한 개념**: 배열의 유효 인덱스 범위는 0부터 `len(array)-1`까지이며, `len(array)`는 범위를 벗어난 값이라는 개념.

**알게 된 사실**: 오른쪽 포인터의 초기값은 배열의 마지막 유효 인덱스인 `len(input_list) - 1`이어야 하며, `len(input_list)`를 그대로 사용하면 인덱스 접근 시 `IndexError`가 발생한다.

**개념이 포함된 섹션**: PL

### 개념 학습 정리 - 투 포인터 이동 방향 로직

**문제 상황**: 두 포인터가 가리키는 값의 합이 목표값보다 클 때, 오른쪽 포인터를 `right += 1`로 이동시킴.

**부족한 개념**: 정렬된 배열에서 투 포인터가 좁혀지는 방향은 합의 크기와 반대로 움직여야 한다는 개념. 합이 크면 값을 줄여야 하므로 큰 값 쪽 포인터를 안쪽으로, 합이 작으면 작은 값 쪽 포인터를 안쪽으로 이동시켜야 한다.

**알게 된 사실**: 합이 목표값보다 클 때는 오른쪽 포인터를 왼쪽으로 좁혀야(`right -= 1`) 합이 줄어들고, 합이 작을 때는 왼쪽 포인터를 오른쪽으로 넓혀야(`left += 1`) 합이 늘어난다. 이동 방향이 반대로 적용되면 두 포인터가 서로 멀어져 반복문이 목표값에 수렴하지 못한다.

**개념이 포함된 섹션**: Algorithms

### 개념 학습 정리 - 내장 함수명과 변수명 충돌

**문제 상황**: 두 값의 합을 저장하는 변수명으로 `sum`을 사용함.

**부족한 개념**: `sum`은 파이썬 내장 함수(built-in function)명이며, 동일한 이름으로 변수를 선언하면 해당 스코프 내에서 내장 함수가 가려진다(shadowing)는 개념.

**알게 된 사실**: 변수명이 내장 함수명과 겹치면 당장 에러는 발생하지 않지만, 이후 같은 스코프에서 `sum()` 함수가 필요한 경우 호출이 불가능해진다. `total` 등 겹치지 않는 이름을 사용하는 것이 안전하다.

**개념이 포함된 섹션**: PL

## 260919

### 개념 학습 정리 - range()를 이용한 반복 구간 순회

**문제 상황**: 슬라이딩 윈도우 문제에서 반복문 작성 중 `for i in (len(input_list)-1-input_int):`와 같이 정수를 직접 반복 대상으로 사용하려 함.

**부족한 개념**: 정수는 반복 가능한 객체(iterable)가 아니므로 직접 순회할 수 없으며, 정수 범위를 순회하려면 `range()` 함수로 반복 가능한 객체를 생성해야 한다는 개념.

**알게 된 사실**: `for i in range(n):`은 0부터 n-1까지의 정수 시퀀스를 생성해 순회하는 구조이며, 정수 자체를 `for ... in` 뒤에 바로 사용할 수 없다.

**개념이 포함된 섹션**: PL

### 개념 학습 정리 - 재계산 방식과 누적 갱신 방식의 시간복잡도 차이

**문제 상황**: 슬라이딩 윈도우 합을 구할 때, 매 구간마다 `while index < i+k-1: new_sum += input_list[index]`처럼 내부 반복문으로 K개를 처음부터 다시 더하는 방식으로 작성함.

**부족한 개념**: 구간이 한 칸 이동할 때 이전 구간 합을 재사용하지 않고 매번 처음부터 합산하면, 겉보기엔 정답이 나오더라도 시간복잡도가 O(N×K)로 유지되어 슬라이딩 윈도우 기법을 적용하는 의미가 사라진다는 개념.

**알게 된 사실**: 슬라이딩 윈도우의 핵심은 이전 구간 합에서 빠지는 값을 빼고 들어오는 값만 더하는 O(1) 갱신이며, 이를 N번 반복해 전체 O(N)을 달성한다. 내부 반복문 유무로 두 방식의 시간복잡도가 갈린다.

**개념이 포함된 섹션**: Algorithms

### 개념 학습 정리 - 역할이 다른 변수의 분리

**문제 상황**: 슬라이딩 윈도우 최댓값을 구할 때, "현재 구간 합"과 "지금까지의 최댓값"을 하나의 변수(`result`)로 처리하여 값을 갱신함.

**부족한 개념**: 현재 구간 합은 매 반복마다 무조건 갱신되어야 하는 값이고, 최댓값은 현재 구간 합과 비교했을 때만 조건부로 갱신되는 값이므로, 역할이 다른 두 값을 하나의 변수에 담으면 다음 반복의 갱신 계산(빼고 더하기)이 잘못된 기준값을 사용하게 된다는 개념.

**알게 된 사실**: 변수를 `window_sum`(현재 구간 합, 매 반복마다 갱신)과 `max`(누적 최댓값, 조건부 갱신)로 분리해야, 다음 구간 합 계산이 항상 직전 구간의 정확한 합을 기준으로 이루어진다.

**개념이 포함된 섹션**: Algorithms

### 개념 학습 정리 - 인덱스 경계값(off-by-one) 계산

**문제 상황**: 슬라이딩 윈도우 구현 중 초기 윈도우 범위(`while index < k-1`), 반복 시작/종료 조건(`i < len(input_list)-k-1` 등), 빠지는 값의 인덱스(`input_list[i]` vs `input_list[i-1]`)에서 여러 차례 경계값 오류가 반복 발생함.

**부족한 개념**: 구간의 끝 인덱스를 포함(inclusive)할지 제외(exclusive)할지, 그리고 "새 윈도우의 시작 인덱스(`i`)"와 "빠지는 값의 인덱스(`i-1`)"가 서로 다르다는 것을 명확히 구분하지 못함.

**알게 된 사실**: K개 구간은 시작 인덱스부터 시작 인덱스+K-1까지이며(끝 포함), 마지막 유효 시작 인덱스는 `len(array)-k`다. 윈도우가 `i`로 이동했다는 것은 직전 구간의 시작값(`i-1`)이 빠지고 새 값(`i+k-1`)이 들어온다는 뜻이므로, 이동 방향과 인덱스 관계를 식으로 먼저 세운 뒤 코드로 옮겨야 오류가 줄어든다.

**개념이 포함된 섹션**: Algorithms

### 개념 학습 정리 - 파이썬 음수 인덱싱과 조용한 오류

**문제 상황**: 반복문의 시작값을 `i=0`으로 설정했을 때 `input_list[i-1]`이 `input_list[-1]`로 계산되어, 에러 없이 배열의 마지막 요소를 잘못 참조함.

**부족한 개념**: 파이썬은 음수 인덱스를 배열 끝에서부터의 위치로 해석해 정상적으로 값을 반환하므로, 의도하지 않은 음수 인덱스 접근이 예외(오류)를 발생시키지 않고 조용히 잘못된 값을 반환한다는 개념.

**알게 된 사실**: 인덱스 계산 실수는 대부분 `IndexError`로 드러나 발견하기 쉽지만, 음수 인덱스로 귀결되는 실수는 에러 없이 통과되어 결과값 검증 없이는 발견하기 어렵다. 인덱스 변수가 0 이상인지 별도로 검증하거나, 여러 입력값으로 결과를 대조하는 습관이 필요하다.

**개념이 포함된 섹션**: PL

### 개념 학습 정리 - 조건부 표현식(conditional expression) 문법

**문제 상황**: 배열 회전 문제에서 K값 정규화를 위해 `k = k % len(input_list) if len(input_list) < k`로 작성함.

**부족한 개념**: 파이썬의 조건부 표현식(`값1 if 조건 else 값2`)은 `if`와 `else`가 모두 있어야 완전한 문장이 되며, `else`가 없으면 `SyntaxError`가 발생한다는 개념.

**알게 된 사실**: 조건부 표현식은 값을 반환하는 표현식이므로, 조건이 거짓일 때 반환할 값(`else` 절)을 반드시 명시해야 한다. 일반 `if` 문(조건에 따라 실행할 코드 블록을 선택)과 달리, 조건부 표현식은 두 경우 모두에서 값을 만들어내야 하는 구조라는 차이를 구분해야 한다.

**개념이 포함된 섹션**: PL

### 개념 학습 정리 - 슬라이싱에서 k=0과 음수 인덱싱의 상호작용

**문제 상황**: 배열 회전 결과를 `input_list[-k:] + input_list[:-k]`로 구성했을 때, `k=0`인 경우를 조건문으로 별도 분기 처리함.

**부족한 개념**: 파이썬에서 `-0`은 정수 `0`과 동일하게 취급되므로, `input_list[-0:]`은 "뒤에서 0개"가 아니라 `input_list[0:]`, 즉 배열 전체를 의미하게 된다는 음수 인덱싱의 특성.

**알게 된 사실**: 슬라이싱에 변수를 음수로 사용할 때, 그 변수가 0이 될 수 있는 경우는 항상 별도로 검증해야 한다. `-k`가 의도한 "뒤에서 k개 제외"가 아니라 "전체 포함"으로 뒤바뀌는 지점이 바로 `k=0`이기 때문이다. 이는 이전에 정리한 "파이썬 음수 인덱싱과 조용한 오류" 개념과 동일한 원인(음수 인덱스가 에러 없이 다른 의미로 조용히 해석됨)이 반복 재현된 사례다.

**개념이 포함된 섹션**: PL

### 개념 학습 정리 - 정수 나눗셈과 부동소수점 나눗셈

**문제 상황**: 배열 뒤집기 문제에서 반복 종료 조건을 `left < len(input_list)/2`로 작성함.

**부족한 개념**: 파이썬에서 `/`는 항상 부동소수점(float) 결과를 반환하는 나눗셈이며, 정수 인덱스 비교에는 정수 나눗셈(`//`)을 사용해야 한다는 개념.

**알게 된 사실**: `len(input_list)/2`는 배열 길이가 홀수일 때 `.5`가 포함된 실수를 반환한다(예: 5/2=2.5). 파이썬은 정수와 실수를 값으로 비교할 수 있어 결과적으로 동작은 하지만, 인덱스라는 정수 개념을 다루는 자리에 실수를 섞는 것은 의도와 표현이 불일치한다. `len(input_list) // 2`로 정수 나눗셈을 사용하는 것이 인덱스 연산의 의도에 맞는 표현이다.

**개념이 포함된 섹션**: PL

### 개념 학습 정리 - 투 포인터 종료 조건의 상대적 기준과 절대적 기준

**문제 상황**: 배열 뒤집기 문제에서 반복 종료 조건을 `left < right`(상대적 관계) 대신 `left < len(input_list)//2`(절대 위치)로 작성함.

**부족한 개념**: 두 포인터가 대칭적으로 이동하는 경우 두 조건은 결과적으로 동일한 반복 횟수를 만들어내지만, 종료 조건이 실제로 의미하는 바(두 포인터가 서로를 지나치는 시점)와 코드가 표현하는 조건(왼쪽 포인터의 절대 위치)이 다를 수 있다는 개념.

**알게 된 사실**: `left < right`는 "두 포인터의 상대적 관계"를 직접 표현하는 조건이고, `left < len(array)//2`는 "왼쪽 포인터가 특정 위치에 도달했는가"라는 별개의 조건이다. 두 포인터가 항상 같은 속도로 움직이는 문제에서는 두 방식이 같은 결과를 내지만, 포인터의 이동 조건이 비대칭적으로 바뀌는 문제(한쪽만 조건부로 이동하는 경우 등)에서는 절대 위치 기준이 실제 종료 시점(두 포인터가 만나는 시점)을 보장하지 못한다. 반복 종료 조건은 "무엇이 진짜 종료 이유인가"를 기준으로 선택해야 한다.

**개념이 포함된 섹션**: Algorithms
