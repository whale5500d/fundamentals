# RAG

## (Common) Architecture

- RAG는 시스템 패턴이다.
- 외부 지식을 검색하고, LLM 입력 프롬프트로 넣어 답변을 생성하는 시스템 패턴이다.
- 모델 자체를 다시 학습시키는 방식이 아니라, 질문 시점에 필요한 정보를 찾아 함께 사용한다.

## Indexing Step

- "문서 로딩, 전처리, 청킹, 임베딩, 벡터DB 저장" 순의 RAG 내 DB 저장 파이프라인
  - 주요 방법(시계열 기준)
    1. 초기 인덱싱: 1회
    2. 재인덱싱(증분 인덱싱): 문서 변경 시마다(비정기), 기존 벡터를 삭제하고 변경된 문서만 다시 인덱싱

- 인덱싱 품질이 검색에 미치는 영향
  - RAg의 검색 품질이 낮다는 것은 검색 알고리즘 자체의 문제보다, Indexing 품질이 낮은 경우가 많다.

### 1. Document Loading

- 문서 로딩: 다양한 형식의 원본 문서에서 텍스트를 추출하여 RAG 파이프라인에 투입할 수 있는 형태로 변환하는 과정
  - 주로 text, metadata를 함께 반환.
    - text: 파일에서 추출한 텍스트 문자열
    - metadata: 파일명, 페이지 번호, 생성일, 출처 등 부가 정보. 벡터 DB에 함께 저장하면 Metadata Filtering에 활용 가능
  - 주요 방법(가벼운 문서 형식 기준)
    1. txt, markdown: 내장 open() 함수 사용
    2. PDF: PyPDF2, pdfplumber, PyMuPDF
    3. HTML: BeautifulSoup
    4. JSON: 내장 json
    5. CSV: 내장 csv, pandas
    6. DOCX: python-docx

#### (Text Preprocessing (텍스트 전처리))

- 문서에서 추출한 텍스트를 청킹, 임베딩 전에 불필요한 노이즈를 제거하고 정리하는 과정
  - 주요 전처리 작업
    - 특수/제어 문자 제거: `\x00`, `\xad`
    - 공백 정규화
    - 빈 줄 정규화
    - 헤더/푸터 제거: PDF의 반복 헤더, 페이지 번호(`- 3 -`) 제거
    - HTML 태그 제거
    - 유니코드 정규화: NFC/NFKC 정규화

### 2. Chunking

- 청킹: 긴 문서를 검색과 임베딩에 적합한 크기의 텍스트 조각(청크)으로 분할하는 과정
  - RAG 시스템을 처음 구축할 때는 청킹 전략보다 파이프라인 전체가 동작하는지 먼저 검증이 우선
  - 주요 방법(난이도 기준)
    1. Fixed-size Chunking: 고정된 글자 수 또는 토큰 수
    2. Regex & Delimiter Chunking: 줄바꿈, 마침표, 제목 등 구분자
    3. Semantic Chunking: 문장 간 임베딩 유사도
    4. Parent-Child Chunking: 큰 청크(부모)와 작은 청크(자식) 계층

- 청크 크기 가이드라인
  - 너무 작으면 문맥이 부족하고, 너무 크면 검색 정확도가 떨어짐.
  - 용도별 추천 크기
    - 일반 QA: 500~1000자
    - 요약: 1000~2000자
    - 코드: 함수/클래스 단위

### 3. Embedding

- Tokenization: 텍스트를 모델이 처리할 수 있는 최소 단위로 분리하는 과정
  - 주요 방법(크기 단위 기준)
    1. Word 단위: 공백, 구두점 기준으로 문자열 분리
    2. Subword 단위: 빈도 기준 문자열 분리
    3. Character 단위: 글자 기준 문자열 분리
    4. Custom 단위: 개발자가 정한 분리 기준에 따라 문자열 분리

- Text Embedding: 텍스트의 의미를 보존한 채 고정 길이의 숫자 벡터로 변환하는 과정
  - (목적) 텍스트 간 유사도를 계산하기 위함
  - **주요 임베딩 모델**
    | 모델 | 제공자 | 차원 | 최대 입력 | 비용 | 특징 |
    | --- | --- | --- | --- | --- | --- |
    | all-MiniLM-L6-v2 | Sentence Transformers | 384 | 256 토큰 | 무료 (로컬) | • 가볍고 빠름<br>• 학습/실험용에 적합<br>• 영어 중심 |
    | multilingual-e5-large | Microsoft | 1024 | 512 토큰 | 무료 (로컬) | • 다국어 지원<br>• 한국어 성능 우수 |
    | text-embedding-3-small | OpenAI | 1536 | 8191 토큰 | API 유료 | • 비용 대비 성능 우수<br>• 긴 입력 지원 |
    | text-embedding-3-large | OpenAI | 3072 | 8191 토큰 | API 유료 | • 더 높은 정확도<br>• 차원 축소 가능 |
    | embed-v3 | Cohere | 1024 | 512 토큰 | API 유료 | • 검색 특화 모드(search_document/search_query) 지원 |

- Dense Vector: 임베딩 모델이 텍스트의 문맥적 의미를 모든 차원에 분산시켜 표현한 저차원 실수 벡터
  - 원리: 신경망 모델이 대량의 텍스트 데이터를 학습하여 만들어낸다. 학습 과정에서 비슷한 문맥에서 등장하는 단어는 비슷한 벡터를 가져야 한다는 원칙으로 학습한다.

- Sparse Vector
  - 주요 방법(이해 난이도 기준)
    1. BoW(Bag of Words): 단어 빈도
    2. TF-IDF: 단어 빈도 \* 역문서 빈도
    3. BM25: 정보 검색 점수도 표준 알고리즘

- Sentence Transformer를 사용하는 이유: 로컬 환경에서 API 비용 없이 고품질 문장 임베딩을 생성할 수 있고, 데이터가 외부 서버로 전송되지 않아 보안이 필요한 환경에서도 사용할 수 있기 때문.
  - HG에는 수천 개의 Pre-training Model이 등록되어 있음.
  - 용도(검색, 분류, 군집), 언어(영어, 다국어, 한국어), 성능/속도 균형에 따라 선택 가능
  - 필요 시 자체 데이터로 Fine-tuning하여 도메인 특화 성능을 높이는 것도 가능
  - `model.encode()`로 텍스트를 Dense Vector로 변환하는 방식 사용

- BERT vs SBERT
  - BERT: 문장, 단어의 문맥을 깊이 이해하는 데 강한 구조
  - SBERT(Sentence-BERT): 문장 전체를 하나의 벡터로 빠르게 변환하여, 문장 간 유사도 검색을 효율적으로 수행하는 구조
  - 두 문장을 유사도를 비교하려면, BERT에선 두 문장을 하나의 입력으로 넣고 모델이 그 관계를 직접 보아야 했다. 높은 정확도를 제공하지만, 리소스가 크고 검색 속도가 느리다.
  - SBERT에선 각 문장을 벡터화하여, 벡터 간 유사도를 계산한다. 리소스가 작고 검색 속도가 빠르다. 현실적인 시간 내 검색이 가능하다. 문장 검색, 의미 기반 검색, RAG Retrieval, 유사 문장 찾기에 적합하다.

### 4. Vector Store(DB)

- 고차원 벡터 디비를 저장하고 , 유사도 기반의 근사 최접근 이웃(ANN) 검색을 수행하는 과정
  - 주요 구성 요소
    - 벡터 저장소: 임베딩 벡터를 고속 검색 가능한 형태로 저장
    - 인덱스: HNSW, IVF
      - HNSW: 벡터를 여러 층의 그래프로 연결해, 가까운 이웃을 빠르게 찾는 검색 방식
      - IVF: 전체 벡터를 여러 묶음으로 나눈 뒤, 관련 있는 묶음만 골라서 검색 속도 높이는 방식
    - 메타데이터 저장소: 벡터와 함께 원본 텍스트, 출처, 카테고리 등 부가 정보를 저장
    - 유사도 함수: Cosine Similarity, Dot Product 등을 사용하여 벡터 간 유사도 측정
    - 필터링: 메타데이터 조건(날짜, 카테고리 등)으로 검색 범위 제한

## (Query Step) Retrival

- "벡터화한 사용자 질문"을 "벡터 DB에 저장해둔 유사 문서 청크"와 검색하여 반환하는 단계
- 사용자 질문을 DB에서 검색하여 반환하는 단계.
- 질문의 대답을 바로 생성하기 전에 근거 문서를 찾아오는 과정.
  - 이 때 검색 대상은 원본 문서 전체가 아니라, Indexing 단계에서 벡터 DB에 저장해둔 문서 청크.
  - 사용자 질문을 임베딩할 때는 Indexing에서 사용한 임베딩 모델과 동일해야 한다. 벡터 공간 내 의미적 유사성을 비교해야 하기 때문이다.
  - 반환된 Top-K 청크는 추후 Generation 단계에 사용된다.
    - Top-K는 일반적으로 3~5로 시작한다. K가 너무 작으면 문서를 놓칠 수 있고, 너무 크면 무관한 문서가 포함되어 LLM의 답변 품질이 떨어질 수 있다. 또한 K를 늘리면 LLM 프롬프트에 삽입되는 텍스트가 길어져 컨텍스트 윈도우를 많이 사용하고 비용이 증가한다. 이후 페이지에서 다루는 RAG Evaluation 지표(Context Precision 등)를 기반으로 최적 K를 결정한다.

### 2. Similarity Retrieval

- 유사도 검색 방법 (직관적인 방법 기준)
  1. Dot Product(내적): 두 백터의 대응 원소를 곱하여 합산하여 벡터 간 유사도나 관련성을 측정하는 연산 (양수, 0, 음수)
     - FAISS, Pinecone 등 VectorDB가 유사도 측정 방법에 Inner Product 사용
     - Transformer 아키텍처에서 Query, Key 간 관련성 계산에 Scaled Dot-Product Attention 사용
     - 벡터 크기에 영향을 받음. ($-∞$ ~ $+∞) 유사도 기준을 설정하기 어려움. 벡터 노름이 큰 항목이 더 높은 점수를 받을 수 있어, 문서 길이에 따라 관련성에 영향을 받음.
  2. Cosine Similarity(코사인 유사도): 두 벡터가 이루는 각도의 코사인 값으로 방향 유사도를 -1~1 범위로 측정하는 지표
     - 벡터 크기에 영향을 받지 않음. 벡터 크기를 나누어 정규화하므로, 유사도 기준을 설정하기 쉬움. 문서 길이에 관계없이 의미적으로 관련성이 높은 문서 탐색 가능.
     - 1이면 같은 방향, 0이면 무관, -1이면 반대 방향
     - 모델에 따라 검색 결과가 낮을 수 있음.
       - Reranking 모델을 추가하여 검색 결과를 재정렬하거나,
       - 임베딩 모델을 도메인에 맞게 Fine-tuning하면 품질이 개선될 수 있음.
     - ChromaDB, Pinecone, Weaviate 등 VectorDB가 Cosine Similarity를 기본 또는 선택 사용 가능
  3. Cosine Distance: $1- Cosine Similarty$로 계산하여, 작을수록 유사함.
     - 현재 VectorDB가 Similarity인지, Distance인지 판단이 필요함.
  4. Euclidean Distance: 벡터 간 절대 거리를 기준으로 비교, 텍스트 의미 유사도보다는 거리 자체가 중요한 문제에서 더 적합.
     - 벡터 간 절대 거리를 기준으로 비교. ($0$ ~ $∞$)
     - 군집화, 이상 탐지에 유용함.
  - 임계값 설정
    - 임베딩 모델, 문서 길이, 도메인, 검색 목적에 따라 설정할 임계값이 달라짐.
    - 절대 기준이 아니라 실무에서 참고할 수 있는 일반적인 해석 예시
      - 0.8 ~: 매우 유사
      - 0.5 ~ 0.8: 강한 관련성
      - 0.3 ~ 0.5: 약한 관련성
      - ~ 0.3: 낮은 관련성
    - 실무에서는 테스트 질문과 정답 문서를 기준으로 여러 임계값을 실험한 뒤 결정
    - 임계값이 고정 규칙이라기보다, Precision과 Recall의 균형을 조정하는 운영 파라미터

### (고급 기법) Query Expansion

- 적용 단계: 검색 전(Pre-retrieval)
- 검색 시스템에 전달하는 사용자 질문 및 검색어의 검색 범위를 넓히는 기법
  - 주요 확장 방식
    - 유의어 추가: 번역어, 약어, 유의어 등을 함께 넣어 작성
    - Multi-Query: 여러 관점으로 질문 다시 작성
    - Step-back Prompting: 일반적인 상위 질문으로 다시 작성

### (고급 기법) HyDE

- 적용 단계: 검색 전(Pre-retrieval)
- LLM으로 가상 답변을 생성하고, 해당 답변을 임베딩하여 실제 문서를 검색하는 기법
  - 동작 흐름
    1. 질문 수신
    2. 가상 답변 생성: 답변처럼 "보이는" 가상의 문서 생성, 실제 정답이 아니라, 검색에 유리한 답변형 문장임.
    3. 가상 답변 임베딩: 생성된 가상 답변을 임베딩 모델로 벡터화
    4. 벡터 검색: 벡터화한 가상 답변 벡터를 검색에 사용
    5. 결과 반환
  - 효과가 큰 분야
    - 사내 문서 검색, 정책 문서 검색, 제품 소개 문서 검색, 초보자 질문이 많은 서비스형 챗봇
    - 질문은 짧지만, 문서는 설명형인 환경에서 효과가 큼
  - 단점: LLM을 한 번 더 호출하므로 지연 시간과 비용이 늘어남. 따라서, 일괄 적용하기보다 질문이 짧고 모호한 경우, 직접 검색의 재현율이 낮은 경우, 문서가 설명형 문장 위주인 경우와 같이 효과가 기대되는 상황에서 선별적으로 적용하는 것이 일반적임.

### (고급 기법) Hybrid Search

- 적용 단계: 검색 중(Retrieval)
- Dense Vector(의미 유사도)와 Sparse Vector(키워드 매칭) 검색을 결합하여 두 방식의 장점을 동시에 활용하는 검색 기법
- 두 검색을 각각 수행한 뒤, 두 결과의 점수를 가중 합산하여 최종 순위 결정

- RRF(순위 기반 결합) 방식: 여러 검색 결과를 점수가 아니라 순위(rank)만으로 결합하여 최종 순위를 정하는 방식. 실무에서는 Elasticsearch, OpenSearch 등이 RRF를 네이티브로 지원해서, 별도 구현없이 사용 가능
  - RRF의 k=60: RRF 원 논문에서 실험적으로 결정된 기본값. 실무 환경에서 실험적으로 k=60이 좋은 성능을 보임.

### (고급 기법) Reranking

- 적용 단계: 검색 후(Post-retrieval)
- 1차 검색에서 확보한 후보 문서를 별도의 정밀 모델(Cross-Encoder 등)로 다시 평가하여, 질문과 더 관련성 높은 문서가 위로 오도록 순서를 재조정하는 기법
  - 1차 검색: Bi-Encoder 기반 Retrieval, 정확도는 낮지만 속도가 빠름. Top-100
  - 2차 리랭킹: 별도의 정밀 모델(Cross-Encoder 등)로 다시 평가, 속도는 느리지만 정확도가 빠름. Top-5(100개 중 5개)

### (고급 기법) Conversational RAG

- 적응 단계: 이전 대화 기록을 고려하여 질문을 재구성하고, 재구성된 질문으로 검색과 답변을 수행하는 멀티턴 RAG 시스템
  - 동작 흐름
    1. 대화 기록 수집: 이전 턴의 질문-답변 쌍을 수집
    2. 질문 재구성: 현재 질문에 이전 대화 기록까지 전달하여, 질문을 재구성
    3. Retrieval: 재구성된 질문을 임베딩하여 벡터 DB에서 유사 문서 검색
    4. Generation
  - 대화 기록 관리 전략: 대화가 길어질수록 이 기록이 LLM의 Context Window를 빠르게 차지하므로, 관리 전략 필요
    - 최근 N턴 유지: 보통 3~5턴만 유지하고, 오래된 대화는 제거
    - 대화 요약: 이전 대화를 LLM으로 요약한 뒤, 요약본을 유지
    - 슬라이딩 윈도우: 토큰 수 기준으로 최대 길이를 정하고, 초과하면 오래된 턴부터 제거

## (Query Step) Augmentation

### Context Window

- LLM이 한 번의 요청에서 처리할 수 있는 최대 토큰 수
  - 각 구성 요소의 토큰 수를 합산하여 모델의 한도를 초과하지 않도록 관리해야 한다.
  - `컨텍스트 윈도우 - 최대 출력 = 최대 입력`
  - 구성 요소
    - 시스템 프롬프트: 200 ~ 500
    - 검색된 문서: 1,000 ~ 4,000
    - 사용자 질문: 50 ~ 200
    - 생성될 답변: 200 ~ 1,000
    - 합계: 1,450 ~ 5,700
  - 토큰 수에 비례하여 과금되기 때문에, 전체 문서를 삽입하면 비용이 매우 높아짐.
  - 입력이 길어질수록 LLM의 Attention이 분산되어 중간 부분의 정보를 놓치는 "Lost in the Middle" 현상이 발생함.
  - 관리 방식
    1. 모델 한도 확인: 컨텍스트 윈도우 확인
    2. 고정 요소 계산: 시스템 프롬프트와 예상 답변 길이의 토큰 수 계산
    3. 가변 요소 배분: 토큰 예산을 검색 문서(청크 크기 \* Top-K)와 사용자 질문에 배분
    4. 초과 여부 검증: 모든 요소의 합이 모델 한도를 초과하는지 확인

### Prompt Engineering

- 검색된 문서를 근거로만 답변하도록 지시하고, 환각을 줄이며, 출처를 명시하도록 유도하는 RAG 전용 프롬프트 설계 기법
  - 같은 검색 결과라도 설계한 프롬프트에 따라 답변의 정확도와 충실도가 달라지고, 환각을 줄인 신뢰 높은 답변을 만들 수 있음.
  - 시스템 지시(역할, 제약 조건), 검색된 문서(문맥), 사용자 질문을 구조화된 템플릿(프롬프트)에 배치
  - 프롬프트 작성 기법
    - 역할 지정: `당신은 사내 문서 기반 QA 시스템입니다.`
    - 근거 제한 지시: `아래 문서만을 근거로 답변하라.`
      - "참고하여" 대신 "근거로"
    - 불확실성 처리: `문서에 없는 내용은 "해당 정보를 찾을 수 없다"고 답하라.`
      "질문에 답하세요" 대신 "업슬 ㅓㅇㅌ"
    - 문서 삽입: `[문서 1]... [문서 2]...`
    - 질문: `"사용자 질문"`
    - 출력 형식 지정: `"3문장 이내로 답하라."`
      - "짧게" 대신 "3문장 이내로"
  - 몰

## (Query Step) Generation

- LLM이 입력된 텍스트(입력 프롬프트)를 바탕으로 새로운 텍스트(출력 프롬프트)를 만들어내는 과정
  - 동작 흐름
    1. 검색 결과 수신
    2. 프롬프트 구성 (시스템 지시, 검색된 문서, 사용자 질문)
    3. LLM 호출
    4. 답변 반환
